## Format général

Toutes les erreurs renvoient un objet JSON dont `detail` est un **objet
structuré** et stable :

```json
{
  "detail": {
    "error_code": "api_key_surface_not_allowed",
    "message": "This operation is not available through the API key surface.",
    "localized_messages": {
      "en": "This operation is not available through the API key surface.",
      "fr": "Cette opération n'est pas disponible via la surface API par clé."
    }
  }
}
```

| Champ | Rôle |
| --- | --- |
| `error_code` | Identifiant **stable** du type d'erreur : branchez votre logique dessus. |
| `message` | Message par défaut (anglais). |
| `localized_messages` | Textes prêts à afficher, en **FR** et **EN**. |
| `params` *(optionnel)* | Valeurs de substitution (ex. `limit`, `currency`). |

## Exemples réels par code

| Code | `error_code` typique |
| --- | --- |
| `401` | `auth_authorization_header_required` |
| `400` | `auth_authorization_header_not_allowed` |
| `403` | `api_key_surface_not_allowed` (facturation, provisioning téléphonie…) |
| `404` | `workflow_id_not_found`, `knowledge_base_not_found`, … |
| `409` | `revision_conflict` (text-chat) |
| `422` | Erreurs Pydantic (champs manquants/invalides) |
| `500` | `internal_error` |

## Erreurs du catalogue

Chaque erreur métier renvoie le même `detail` objet que ci-dessus, avec des
**messages localisés** (`localized_messages`) en **FR** et **EN**. Exemple :

```json
{
  "detail": {
    "error_code": "knowledge_base_upload_url_failed",
    "message": "Failed to generate upload URL.",
    "localized_messages": {
      "fr": "Impossible de générer l'URL d'upload.",
      "en": "Failed to generate upload URL."
    }
  }
}
```

<Info>
Ces codes sont stables : vous pouvez vous y fier pour afficher un message
utilisateur propre dans la langue de votre interface. Pour un `500`, le
`error_code` est toujours `internal_error` — le détail technique reste
journalisé côté serveur et n'est **jamais** exposé au client.
</Info>

## Conflits `409`

Sur le **text-chat**, un `409` indique un **conflit de révision** (deux écritures
concurrentes). Réaction attendue :

1. Relisez la session : `GET /workflow/{workflow_id}/text-chat/sessions/{run_id}`.
2. Réémettez la requête avec `expected_revision` à jour.

## Stratégie de retry

| Code | Retenter ? |
| --- | --- |
| `502` / `503` / `504` | **Oui**, avec backoff exponentiel |
| `401` | Non |
| `402` | Non, créditez d'abord |
| `403` | Non |
| `422` | Non, corrigez le corps |

<Warning>
Ne retentez jamais en boucle un `402` ou un `401` : vous serez bloqué de la
même manière. Traitez la cause (crédits, clé) avant de réessayer.
</Warning>
